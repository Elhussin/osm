# مراجعة حزمة وصيل المقدمة

التاريخ: 2026-11-09. المصدر: المجلد المحلي Waseel_PI_Document الذي أضافه المستخدم. مراجعة ساكنة دون أي اتصال، ودون اعتماد صلاحية بيانات الدخول الموجودة في الأمثلة.

## المواد ودرجة الاعتماد
- ملف Waseel API v2.0 - Document.xlsx: 18 ورقة، منها طلب/رد الأهلية والموافقة والإلغاء والتواصل وقوائم القيم ومواصفات البصريات. ورقة UPDATE تسجل إنشاء الوثيقة في 2022-06-14 وتعديل v2 في 2022-10-01؛ تاريخ المراجعة الحالي لا يجعلها أحدث إصدار لدى المزود.
- مجموعة PriorAuth - StagingV2.0.postman_collection: 17 طلبًا، بينها مثال Vision. لا توجد أمثلة response محفوظة داخل الطلبات، ولا نموذج رد للمصادقة في المجموعة.
- خمسة ملفات JSON مستقلة: طلب أهلية وأربعة ردود موافقة (approved / partial / pended / outcome Error).
- readm.md يذكر عناوين الإنتاج؛ يحتوي عنوان الأهلية فيه مسافة غير صالحة بعد api. لا يؤخذ منه عنوان حرفي دون تصحيح واعتماد.
- يوجد ملف نصي فارغ؛ لم يحذف لأنه ضمن مواد المستخدم.

`contract-inventory.json` سجل منقح قابل لإعادة التوليد، يحتوي بصمات SHA-256 للملفات التسعة، ومسارات وطرق الطلبات وأسماء حقولها وأنواع القيم فقط، ومواقع حقول Excel. لا يحتوي أسماء العملاء أو أرقامهم أو كلمات المرور أو رموز Bearer أو أجسام الطلبات الأصلية. لا يمثل OpenAPI كاملًا أو اعتمادًا نهائيًا للعقد.

## العمليات المثبتة في Postman
المسار هنا موحد داخليًا إلى {provider_id}؛ المصدر يستخدم صيغ placeholder متعددة وأحد الأمثلة يستخدم رقمًا ثابتًا. يقرأ التطبيق المعرف من إعداد الربط الخاص بالشركة/الفرع، ولا ينسخ الرقم من المثال.

| العملية | الطريقة والمسار | المصدر وحدود المعرفة |
|---|---|---|
| المصادقة | POST /oauth/authenticate | Authentication: جسم username/password وContent-Type؛ طريقة استخراج الرمز ومدة صلاحيته وتجديده غير موثقة برد ضمن الحزمة |
| الأهلية | POST /eligibilities/providers/{provider_id}/request | مثالا Discovery وBenefit-Validation؛ يستخدمان Bearer |
| الموافقة | POST /approvals/providers/{provider_id}/approval/request | أمثلة متعددة بينها Vision وfollow-up وreferral؛ Bearer |
| البحث عن موافقة | GET /nphies-rest-external/providers/{provider_id}/external/approval | PreAuth Search Request، query باسم requestId؛ لا نفترض أنه بديل منع تكرار لأي طلب غير معروف المصير |
| التواصل | POST /nphies-rest-external/providers/{provider_id}/external/approval | PreAuth-Communication، claimResponseId وpayloads ومرفقات؛ يلزم تحديد ربط claimResponseId بمراجع الرد الفعلية |
| إلغاء الموافقة | POST /approvals/providers/{provider_id}/approval/cancel/request | approvalRequestId وcancelReason؛ قيم الإلغاء WI/NP/TAS في LOV، لا تساوي حذف المستند المحلي |

المضيفان الموجودان: api.stg-eclaims.waseel.com وapi.eclaims.waseel.com. المجموعة ليست staging خالصة: Benefit-Validation والبحث يشيران إلى الإنتاج. الإعداد الجديد يجب أن يختار بيئة واحدة صريحة؛ لا يستخدم host كل مثال أثناء التشغيل، ولا يُسمح بانتقال تلقائي من الاختبار إلى الإنتاج.

## الأهلية وجلب بيانات العميل
ورقة Eligibility Request، الصفوف 2–9: transfer، isNewBorn، destinationId، serviceDate، validation، benefits، discovery، beneficiary. `discovery` مخصص عندما يكون تأمين العميل غير معروف؛ `validation` و`benefits` يستخدمان معًا بحسب الوصف. insurancePlan وحقول البطاقة والتغطية لها شروط تختلف حسب الغرض؛ لا نطبق شكل المثال وحده كقانون لكل طلب.

ورقة Eligibility Response: status موصوف Active، لكن outcome وsiteEligibility وcoverages.inforce وnoCoverageFoundReason حقول مستقلة. Active أو HTTP 200 وحدهما ليسا دليل أهلية. تشمل الردود اسم المستفيد والهوية والتغطيات والمنافع ومساهمة العميل؛ تُعرض للمراجعة قبل تحديث الملف المحلي.

لا توجد في الحزمة عملية مستقلة مثبتة لجلب ملف العميل بالهوية فقط. يمكن تصميم خطوة اكتشاف/أهلية تعرض بيانات الرد، لكن لا نفترض أنها تجلب جميع البيانات أو تعمل دون الحقول الإلزامية المدخلة. تبقى عملية جلب العميل المستقلة فجوة W01.

## متطلبات البصريات المؤثرة على نموذج الوصفة
المصدر: PreAuthorization Request!A149:G168، ومثال Preauthorization Request- vISION في Postman.
- type في preAuthorizationInfo هو vision في المثال، وله visionPrescription يحوي dateWritten وprescriber وlensSpecifications.
- prescriber يشير إلى تسلسل careTeam، وليس معرف مستخدم Django مباشرة. يلزم تحقق المراجع بين البنود والوصفة وفريق الرعاية.
- axis في الوثيقة 1–180، cylinder من -12 إلى +12 بخطوة 0.25، sphere من -30 إلى +30 بخطوة 0.25 ومشروط بمنتج lens. هذه قيود إرسال المزود الموثقة محليًا، وليست بديلًا لكل قواعد التسجيل السريري.
- contact له حقول شرطية lensPower وlensBackCurve؛ lensDuration وlensDurationUnit مرتبطان، والوحدات D/WK/MO.
- prismAmount وprismBase موصوفان Mandatory في الصفين 164–165، والمثال يستخدم prismAmount صفرًا رغم وصف نطاق موجب يبدأ من 0.25. لا نصلح هذا التعارض بالتخمين ولا نرفض كل وصفة لا تحتاج prism قبل سؤال المزود.
- المثال يحتوي multifocalPower بينما جدول الحقول لا يوضحه في قسم البصريات؛ لا نعتمد تمثيل ADD النهائي قبل حسمه.
- ورقة PreAuth and Service Type، الصفوف 28–30: Vision يسمح medical-devices / procedures / services. يلزم اعتماد قائمة الأكواد المتاحة واتفاق التسعير، لا تحويل SKU تلقائيًا إلى كود خدمة تأمين.

البديل الجديد سيحفظ الوصفة العامة دون قص أو تعديل القيم لإرضاء موصل التأمين. التحقق الخاص بالإرسال يرفض غير القابل للإرسال برسالة واضحة ويحفظ سبب الرفض.

## الأسعار والقرارات
PreAuthorization Request، الصفوف 117–134: quantity وunitPrice وfactor وnet وpatientShare وpayerShare وtotalNet، مع taxPercent وdiscount ومراجع careTeamSequence. unitPrice بدقتين وfactor حتى ست منازل وtotalNet تقريب إلى منزلتين بحسب الوصف. توجد أوصاف حسابية ملتبسة؛ لا يُشتق منها محرك ضريبي أو مسؤولية مالية نهائي قبل W05.

الردود المستقلة تثبت ضرورة الفصل بين:
- outcome = Processing Complete مع status = approved أو partial.
- outcome = Queued مع status = pended، وهو انتظار وليس رفضًا أو نجاح موافقة.
- outcome = Error مع status قد يكون فارغًا؛ خطأ المعالجة ليس قرار رفض تأميني تلقائيًا.
- responseDecision وitems[].itemDecision: تحفظ قرارات البنود والمبالغ والمراجع، ولا تعمم موافقة رأس المستند على كل بند.

تحفظ مراجع transactionId/outgoingTransactionId وapprovalRequestId وapprovalResponseId وpreAuthRefNo حسب نوع الرد؛ لا يُستخدم أحدها بدل الآخر. أسماء مثل providertransactionlogId وbillabelEnd وeligibiltyIdentifierUrl تظهر بتهجئات المصدر؛ لا تصحح تلقائيًا في JSON المرسل دون عقد مؤكد. errors قد تكون مصفوفة نصوص أو عناصر ذات coding؛ يلزم دعم الشكلين وإبقاء الفشل غير المعروف ظاهرًا.

## خطة التنفيذ والاختبار المعدلة
R02/R04: ربط ProviderConfig بالشركة والفرع، وفصل هوية مقدم الخدمة عن payer/destination ومعرفات المستخدمين. السجلات العامة لا تحفظ بيانات المرضى أو المفاتيح. هذه متطلبات تصميم، لم تُنفذ النماذج بعد.

R06/R07: حفظ معاني الوصفة وأكواد الخدمات وإصدار mapping منفصل لكل مزود، دون تغيير بيانات المنتج الأصلية أو حدود الوصفة العامة.

R12: بناء طلبات الأهلية وموافقة Vision، والقرار الجزئي/الانتظار/خطأ المعالجة وقرارات البنود، والتواصل والإلغاء كعمليات منفصلة، وتهيئة المطالبات داخليًا فقط. اختبارات ببيانات صناعية؛ لا تنسخ أمثلة المرضى إلى fixtures التطبيق.

R13: تنفيذ الاتصال بعد حسم فجوات العقد. اختبارات لكل endpoint موثق، وفصل staging/production، واستقلال حسابات شركتين، و401/403/429/timeout، وerrors بنوعيها، ومنع تكرار الأثر، ثم sandbox. لا تسجل R12 أو R13 كمنجزة بسبب اكتمال هذه المراجعة.
