# ADR 0005: تنفيذ الهوية والصلاحيات R04

التاريخ: 2026-11-09. الحساب تابع لشركة واحدة وفق ADR 0003. التنفيذ لا يغير هذا القرار.

## حدود التنفيذ
أضيف تطبيق access محلي لكل شركة: Branch وRole وRoleAssignment وBranchAccess وAccessLock وAuditEvent وProviderConnection. قوالب الأدوار العشرة وأكواد الأفعال ثابتة ومراجعة في الكود؛ لا محرر أدوار مخصص في R04. جدول Role يثبت القالب فقط، ولا يوجد جدول RolePermission قابل للتحرير. هذا يحل محل التصور المنطقي لـRolePermission في ACCESS_MODEL؛ أي تخصيص لاحق يحتاج resolver واختبارات المنح المتعدي قبل تفعيله، ولا يمنح تغيير اسم الدور صلاحية.

قيود PostgreSQL تمنع تعيين دور شركة لفرع أو دور فرع دون فرع، وتمنع تكرار التعيين. خدمات المنح تفحص roles.manage وكل أفعال الدور المطلوب في النطاق نفسه؛ members.manage لا يكفي لإعادة تعيين كلمة مرور صاحب امتيازات أعلى. لا تجاوز عبر staff/superuser.

كل عملية إدارة عضوية/منح/ملكية تأخذ قفل AccessLock داخل معاملة، وتعيد تحميل المستخدم والتعيينات الحالية من المخطط. نقل الملكية يتحقق من كلمة مرور المالك الحالي ومن بديل نشط؛ لا يمكن تعطيل آخر مالك. المستخدم والفرع يعطلان بدل حذف تاريخ الأعمال.

## الإنشاء والاستعادة
إنشاء شركة عبر أمر deployment فقط، باسم schema داخلي مولد ومفتاح إعادة محاولة UUID. يحجز النطاق في public دون نشره، ويرحل المخطط ويزرع الأدوار والمالك والفرع الرئيسي ويمنح runtime، ثم يعلن ready ويربط النطاق. الخطأ يبقي الشركة failed بلا نشر نطاق؛ إعادة المحاولة بنفس المفتاح تستأنف المخطط دون حذف بياناته أو استبدال بيانات المالك الموجودة في سجل الإنشاء. حفظ Company لا ينشئ schema تلقائيًا.

## الدخول والروابط
دخول وخروج HTML مع CSRF، وتقييد محاولات الدخول في قاعدة الشركة، وربط session صراحة بـcompany UUID. استرجاع نفس اسم الدخول أو cookie في شركة أخرى لا يمنح وصولًا. الجلسة المعطلة/كلمة المرور المتغيرة لا تستمر بصلاحية قديمة. Cookie الإنتاج host-only وSecure وHttpOnly.

الدعوات وإعادة تعيين كلمة المرور يصدرها مسؤول مخول عبر خدمات داخلية، ويستهلكها صاحبها بنموذج HTML. الرمز موقع ومربوط بالشركة والمستخدم والغرض والمدة، ومخزن كـdigest فقط وأحادي الاستخدام. رابط العرض يكون `/auth/link/invite/#token=...` أو reset؛ fragment لا يذهب إلى access-log، والصفحة تمحوه من العنوان بعد وضعه في الحقل المخفي. لا طباعة للرمز أو كلمة المرور في audit.

لم تجهز قناة إرسال بريد/رسائل فعلية أو نموذج «نسيت كلمة المرور» العام في هذه المرحلة؛ تسليم الدعوة ومحرر الإدارة وتجربة الاستعادة جزء من R05 وإعدادات الإرسال المعتمدة. لا ترسل الاختبارات رسائل لأشخاص. لا يوجد endpoint عام لإنشاء شركة أو إصدار رموز لمسؤول غير مخول.

## التدقيق والتكامل
التدقيق يسجل actor/action/target/request UUID/time فقط، بلا payload حر. request UUID عبر ContextVar يعاد ضبطه بعد كل طلب. منح runtime تمنع UPDATE/DELETE على AuditEvent وتمنع تعديل تاريخ migrations؛ مالك قاعدة النشر يظل مخولًا تقنيًا، ولا ندعي حمايته من DBA.

ProviderConnection يخزن مرجع سر فقط وفرعًا وبيئة ومعرف مزود. التحقق محلي؛ لا قراءة لخزان أسرار أو اتصال بوصيل. run_authorized حد داخلي لاختيار الشركة وإعادة فحص الدور واستعادة السياق؛ توثيق الرسائل والـqueue والإرسال الفعلي R13.

## الواجهة والاختبارات
أضيف HTML أولي للدخول والحساب والفروع والتدقيق واستهلاك الروابط؛ لا عميل API جديد لبناء هذه الشاشات. التصميم المتجاوب المتكامل وتجربة إدارة الأعضاء والفروع في R05. طلبات Client/CSRF وقاعدة PostgreSQL والتزامن اختبارات فعلية، لكنها لا تدعي فحص متصفح بصري.

المراجع التقنية التي راجعت عند التنفيذ: [Django authentication](https://docs.djangoproject.com/en/5.2/topics/auth/default/)، [CSRF](https://docs.djangoproject.com/en/5.2/howto/csrf/)، [select_for_update](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-for-update). قيود العمل واختيار القوالب الثابتة قرارات هذا المشروع.
