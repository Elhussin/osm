# ADR 0002: استمرار استخدام PDM وفصل إعدادات التطبيق

التاريخ: 2026-11-09. الحالة: معتمد لمسار العمل؛ تثبيت البيئة والتحقق منها ضمن R03.

## السياق والدليل
المستخدم أكد استخدام PDM سابقًا. osmBack/pyproject.toml وosmBack/pdm.lock موجودان، وREADME القديم يوثق pdm install وpdm run python manage.py. Dockerfile القديم يستخدم pip وrequirements.txt، لذلك لا يوجد مسار اعتماديات موحد حاليًا. config_loader.py يستخدم python-decouple لتحميل ملف بيئة؛ PDM ليس بديلًا لملفات إعداد التطبيق.

## القرار
- نستمر مع PDM لإدارة اعتماديات Python وتشغيل أوامر المشروع الجديد.
- ينشأ pyproject.toml وpdm.lock جديدان داخل rebuild/ في R03، باعتماديات ضرورية فقط. لا نعدل lock يدويًا ولا ننسخ القائمة القديمة كاملة.
- تثبت نسخة Python وPDM المختبرة ويولد lock فعليًا، ثم يُختبر تثبيت نظيف من lock في CI. لا نعلن إصدارات أو أوامر تثبيت مجربة قبل تنفيذها.
- PDM يدير بيئة التنفيذ؛ متغيرات النظام أو ملف بيئة محلي غير متتبع يدير أسرار وقيم التطبيق. ملف example بالقيم الوهمية فقط.
- توحد بيئة التطوير وCI والحاوية على مصدر اعتماديات واحد؛ export إن لزم يولد آليًا ولا يصبح ملفًا يدويًا موازيًا.
- لا يُستخدم __pypackages__ المرجعي أو ملف بيئة قديم لربط التطبيق الجديد بالبيانات الأصلية.

## بوابة التحقق R03
اكتشاف pdm/python الفعليين، إنشاء البيئة، تثبيت نظيف، فحص Django، migrations على PostgreSQL اختبار مستقل، ثم اختبارات العزل والإعداد الناقص. لا يثبت وجود pdm.lock صلاحية التشغيل.

## نتيجة هذه الجلسة
Get-Command pdm لم يجد أمرًا. Python/py يشيران إلى WindowsApps؛ لم نثبت حزمًا ولم نشغل قاعدة بيانات. لا تتطلب أعمال حصر R01 تشغيل التطبيق.

تحديث R03: ثُبت PDM 2.29.7 في rebuild/.tools/pdm، وأنشئت .venv وpdm.lock جديدان فعليًا. نجحت الاختبارات المحلية على PostgreSQL مستقل؛ التفاصيل والإصدارات في ADR 0004. لا حاجة لتثبيت PDM في Python العام.
