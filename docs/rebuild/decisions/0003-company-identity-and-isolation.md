# ADR 0003: حساب تابع لشركة واحدة وعزل مخطط لكل شركة

التاريخ: 2026-11-09. الحالة: معتمد للتنفيذ في R03/R04. اعتمد المستخدم صراحة أن كل حساب يتبع شركة واحدة فقط. هذا القرار يحسم تفصيل العزل المؤجل في ADR 0001؛ لا يعني أن عزل قاعدة البيانات نُفذ أو اختُبر بعد.

## القرار
PostgreSQL واحدة للتشغيل الجديد، ومخطط مستقل لكل شركة باستخدام django-tenants. دليل الشركات والنطاقات فقط في public. مستخدمو الشركة وكلمات مرورهم وجلساتهم وأدوارهم وفروعهم وبيانات ERP داخل مخطط الشركة، دون جدول مستخدمين أو جلسات مشترك.

الحساب لا يمتلك عضوية في شركات متعددة. نفس البريد أو اسم الدخول في شركتين يعني حسابين منفصلين وكلمتي مرور وجلستين مستقلتين. لا ربط تلقائي بالهوية أو البريد، ولا نقل حساب أو استرداد كلمة مروره من نطاق شركة أخرى.

## بدائل درست
| البديل | التقييم في هذا المشروع |
|---|---|
| جداول مشتركة مع company_id وRLS | ممكن تقنيًا، لكنه يحتاج ضبط RLS وسياسات كل جدول ودور اتصال واختبارًا شاملًا؛ لا نضيف هذا التحول الآن مع غياب حاجة لحساب متعدد الشركات |
| قاعدة مستقلة لكل شركة | فصل أقوى بصلاحيات اتصال مستقلة، وتكلفة أعلى في إدارة الاتصالات والترحيل والنسخ؛ يؤجل لعملاء يحتاجون فصلًا مخصصًا بقرار مستقل |
| مخطط لكل شركة ومستخدمون مشتركون | لا نحتاج تعقيد عضويات شركات متعددة؛ يخالف نموذج الحساب الذي اختاره المستخدم إن استُخدم لتشارك الحساب |
| مخطط لكل شركة والمصادقة داخله | الاختيار: حدود واضحة لحساب الشركة، واستفادة من المعرفة المرجعية دون نسخ إعداداتها المتضاربة |

## توزيع التطبيقات قبل أول migration
| الموضع | المكونات المخططة | ممنوع |
|---|---|---|
| public / SHARED_APPS | django_tenants وdirectory (Company/CompanyDomain)، سجل provisioning تقني بلا بيانات مرضى | users/auth/sessions/ERP، وكلمات المرور أو بيانات وصيل |
| مخطط الشركة / TENANT_APPS | identity.User المخصص، contenttypes/auth/sessions، access/branches/audit، وبقية ERP والتكاملات | CompanyDomain محلي مكرر، أو مصادقة مشتركة تسقط إليها الطلبات |

لا يوضع identity/auth/sessions في القائمتين. AUTH_USER_MODEL يشير إلى identity.User الموجود في 0001_initial. directory لا يعتمد على FK للمستخدم؛ لا علاقات عمل عابرة للمخططات. صلاحيات Django وis_staff/is_superuser لا تتجاوز تفويض ERP. الإدارة الفنية، إن فُعلت داخل الشركة، تمر بضوابط منفصلة ولا تستخدم لتعديل مستندات مرحّلة.

الموقع العام لا يوفر login أو Django Admin يعتمد على جداول auth غير الموجودة في public. إنشاء الشركة وأول مالك في البداية عبر أمر provisioning مخصص، بحساب نشر محدود، وليس endpoint عامًا. أي بوابة دعم مركزية لاحقة تحتاج قرارًا منفصلًا؛ لا حساب دعم عام يصل تلقائيًا لبيانات جميع الشركات.

## هوية السياق وتسلسل الطلب
1. تحقق المضيف مقابل إعدادات ALLOWED_HOSTS وCompanyDomain الكامل المعتمد، وليس تقسيم أول جزء أو قبول schema من header/body/query. لا fallback لشركة أولى أو public عند مضيف غير معروف.
2. تحقق أن الشركة active وready وأن المخطط مهيأ. لا تستقبل provisioning أو failed حركة تشغيل.
3. اضبط مخطط الشركة قبل قراءة session أو User؛ middleware تحديد الشركة يسبق SessionMiddleware وAuthenticationMiddleware.
4. حمّل المستخدم من المخطط المحدد، وتحقق النشاط، وابن CompanyContext موثوقًا يتضمن company UUID وschema وactor UUID. لا تعيد استخدام instance مستخدم أو queryset من سياق شركة أخرى.
5. تحقق صلاحية العملية ونطاق الفروع، وطبّق التصفية قبل pagination/count/lookup/تصدير. إثبات ملكية resource لا يأتي من company_id الذي يرسله المتصفح.
6. بعد الخطأ أو الطلب أو مهمة الخلفية يعاد الاتصال إلى سياق آمن. R04 يختبر A ثم B على الاتصال نفسه وعند الاستثناء؛ لا تعتمد mutable global أو thread-local غير مضمون مع ASGI.

## الدخول والجلسات
- الدخول على نطاق الشركة، وجلسة server-side داخل مخططها. الإنتاج HTTPS وcookie باسم __Host-erp_session، Secure وHttpOnly وPath=/ دون Domain. CSRF token وفحص origin لجميع العمليات المغيرة للحالة.
- لا مشاركة cookies بين نطاقات الشركات ولا تحويل JWT قديم. تبديل الفرع يغير عرض الفرع بعد تحقق التفويض؛ لا يغير الشركة ولا المخطط.
- الدعوة واستعادة كلمة المرور وأي رابط يحمل سياق الشركة والهوية والغرض والصلاحية؛ استهلاك في نطاق آخر يُرفض، مع رسالة لا تكشف وجود المستخدم.
- تغيير اسم المجال alias لا يعيد استخدام جلسة شركة أخرى. الربط الصريح لعدة domains بنفس الشركة ممكن، لكنه لا يفتح مشاركة جلسة عامة.
- إلغاء الحساب أو الدور يظهر في الطلب التالي؛ لا token طويل يحتفظ بصلاحيات قديمة. لا تعد هذه القواعد منفذة قبل اختبارات HTTP في R04.

## حدود المخططات
المخطط ليس حاجزًا أمنيًا مطلقًا: حساب قاعدة بيانات يملك وصولًا إلى مخططين يستطيع الوصول إليهما. الاختيار يقلل مشاركة الجداول ولا يحمي من حقن SQL أو اختراق دور اتصال واسع. فصل دور migration/provisioning صاحب DDL عن دور runtime؛ لا CREATE schema/table أو صلاحيات superuser للتطبيق، ولا CREATE لمستخدمي الشركات في public أو مخططات الشركة. لا SQL ديناميكي من اسم شركة يرسله العميل.

لا ينشئ runtime مخططًا من Company.save(). الإنشاء يأخذ قفل provisioning وحالة initializing→ready أو failed؛ لا نشر نطاق جاهز قبل نجاح migrations والبذور. لا يُعاد اسم schema لشركة أخرى بعد تعطيلها. أسماء schema داخلية مولدة ومتحقق منها، لا أسماء تجارية.

## أثر التشغيل والتكامل
- كل مهمة خلفية تحمل company UUID وactor UUID أو هوية خدمة محلية والغرض وrequest ID، وتحل الشركة من الدليل. تدخل tenant_context موثوقًا وتتحقق الصلاحية الحالية قبل الأثر؛ لا تحمل schema غير موثوق أو instance ORM عبر queue.
- مفاتيح cache وملفات الوسائط والتصدير والأقفال وidempotency تبدأ بمعرف الشركة؛ يضاف الفرع/المستخدم حسب المحتوى. التنزيل يمر ببوابة وصول؛ لا يكفي اسم ملف صعب التخمين.
- ProviderConnection داخل الشركة، مربوط بفرع وبيئة وprovider_id وsecret_ref؛ معرف المزود ليس معرف الشركة أو الدافع أو المستخدم. لا نسخ tokens في public أو logs. اختيار اتصال فرع آخر يحتاج صلاحية فرعه؛ لا fallback لاتصال شركة أخرى.
- نقل مخزون بين فروع الشركة يحتاج صلاحية المصدر والوجهة. عمليات بين شركتين، إن طلبت مستقبلًا، معاملات تجارية منفصلة موثقة وليست FK أو نقلًا مباشرًا بين schema.

## بوابة التنفيذ
R02 يسلم القرار ونموذج البيانات ومصفوفة التهديدات واختبارات سياسة مجردة. R03 يثبت ترحيل public وشركتين جديدتين دون اعتماد legacy. R04 يثبت على PostgreSQL وHTTP غياب auth من public، وعزل كلمات المرور والجلسات والروابط، وفروعًا بصلاحيات مختلفة، واستعادة السياق. لا تعوض اختبارات Python المجردة هذه الأدلة.

## مصادر القرار
الاختيار نفسه حكم تصميم مبني على متطلبات المستخدم. التفاصيل التقنية راجعت في 2026-11-09:
- [django-tenants: توزيع التطبيقات والـmiddleware](https://django-tenants.readthedocs.io/en/stable/install.html): ضبط SHARED_APPS/TENANT_APPS وتحديد المخطط قبل بقية الطلب.
- [Django: تخصيص المستخدم](https://docs.djangoproject.com/en/5.2/topics/auth/customizing/): وضع النموذج المخصص في أول migration. إصدار الاعتماد الفعلي يحسم في R03.
- [PostgreSQL: المخططات وصلاحيات search_path](https://www.postgresql.org/docs/18/ddl-schemas.html): المخططات لا تمنع الوصول لمن لديه الصلاحيات؛ CREATE في مخطط موثوق له أثر أمني.
