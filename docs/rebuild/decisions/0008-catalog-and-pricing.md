# ADR 0008: الكتالوج ومتغيرات البصريات والتسعير — R07

التاريخ: 2026-11-09. امتداد ADR 0001 و0003 و0005 و0007؛ لا تغيير لقوالب الأدوار أو الهوية.

## النموذج
catalog تطبيق tenant فقط. Product يملك رمزًا ثابتًا ونوعًا واسمًا وعلامة وموديلًا؛ Variant يملك SKU وباركودًا اختياريًا ووحدة بيع ومواصفات ثابتة وسعرًا أساسيًا وحالة. الأسعار SAR قبل الضريبة؛ لا تكاليف شراء أو رصيد مخزون أو مخازن مالية أو ترحيل داخل model.save. العلامة والموديل نصوص بسيطة حاليًا، دون نسخ EAV ووراثة الجداول والمفاتيح المبنية على صفات من أسماء حرة من النسخة القديمة.

المواصفات JSON بإصدار schema=1، تُبنى بخدمات عبر مخططات صريحة في specifications.py لكل نوع، وليست JSON حرًا في الواجهة أو حقولًا يعرّفها المستخدم. يُرفض الحقل المجهول والقيمة غير المطابقة، ثم يُنشأ fingerprint SHA256 من النوع والوحدة والمواصفات المطبعة. قيد unique(product,fingerprint) يحمي التكرار داخل المنتج؛ SKU والباركود فريدان في الشركة، ويمكن تكرارهما في شركة أخرى. تطبيع whitespace/NFKC/casefold للنصوص وترتيب الطلاءات وإزالة تكرارها وتوحيد Decimal والصفر السالب يمنع تكرار تمثيلات المواصفات نفسها؛ لا قاموس يدمج مرادفات أسماء المواد والألوان بين لغتين.

هذه مفاضلة معلنة: PostgreSQL يفرض وحدانية fingerprint والأسعار والتواريخ والكمية والنطاق، لكنه لا يعيد تنفيذ كل مخطط JSON. لا CRUD خام أو قبول fingerprint من المتصفح؛ كل كتابة عبر الخدمة. لا ادعاء حماية من DBA أو حقن SQL بدور واسع. إن احتاج البحث التحليلي على كل خاصية لاحقًا، يراجع نقل الخصائص لأعمدة/فهارس بمقياس فعلي قبل إضافة تعقيد.

## مصفوفة المتغيرات والوحدات
| النوع | المواصفات الأساسية | وحدة البيع |
|---|---|---|
| إطار | لون، عرض العدسة، الجسر، الذراع؛ مادة وشكل اختياريان | قطعة |
| عدسة مخزنية | مادة، index، قطر، تصميم، لون وطلاءات، SPH وCYL | عدسة واحدة أو زوج، باختيار صريح |
| عدسة تصنيع RX | مادة، index، قطر، تصميم، لون وطلاءات | عدسة واحدة أو زوج |
| عدسة لاصقة | مادة، قطر، BC، SPH/CYL/AXIS/ADD، حجم العلبة ودورية الاستبدال، لون ونسبة ماء اختياريان | علبة |
| إكسسوار | لون ومقاس اختياريان | قطعة |
| جهاز | مواصفة/إصدار | قطعة |
| خدمة | وصف | خدمة |

RX تصميم قابل للتصنيع؛ قوى المريض تأتي من إصدار الوصفة وطلب التصنيع R10، ولا تتحول إلى مخزون SKU لكل مريض. محور اللاصقة يُطلب عند CYL غير صفرية ويُترك فارغًا مع CYL صفر؛ عدسة المخزون لا تحمل محور تركيب. CYL وADD غير المدخلتين في الكتالوج تُطبعان إلى0 باعتبار عدم وجود قوة إضافية للصنف؛ هذا قرار مختلف عن clinical حيث عدم إدخال القياس ليس صفرًا. حدود الأبعاد والقوى وخطوة0.25 هي تحقق إدخال برمجي، وليست اعتمادًا طبيًا أو التزامًا بتوفر الصنف لدى المصنع.

وحدة البيع جزء من هوية المتغير والسعر، ولا تحويل ضمني بين الزوج والقطعة أو فتح علبة. الكمية عدد صحيح1–1000000 بوحدة المتغير. المخزون R08 يجب أن يحتفظ بالوحدة نفسها أو يبني تحويلًا صريحًا مختبرًا؛ لا تستنتج تحويلًا من الاسم. انتهاء صلاحية/دفعات اللاصقة والتسلسلات للأجهزة بيانات مخزون R08، لا جزءًا من SKU أو قائمة أسعار R07.

## ثبات الهوية والتعديل
رمز المنتج ونوعه وSKU والباركود والوحدة والمواصفات لا تتغير بعد الإنشاء؛ المواصفات المختلفة متغير جديد. يمكن تعديل الاسم/العلامة/الموديل/الحالة والسعر الأساسي بإصدارات expected_version، وإيقاف بدل حذف. منح runtime تمنع DELETE على الجداول الثلاثة وتمنع UPDATE لأعمدة الهوية/المواصفات، وتسمح فقط بأعمدة المنتج الوصفية والسعر والحالة/الإصدار. لا تكفي الصلاحيات الصفية وحدها لحماية الأعمال؛ الخدمات تبقى بوابة التفويض.

امتداد R08-M05 في2026-11-10: إنشاء المتغير يرفض أيضًا أن يطابق SKU باركود متغير آخر أو العكس، بعد التطبيع وتحت AccessLock. إنشاء متغيرات المصفوفة يفحص SKU الجديد مقابل الباركود المحفوظ قبل bulk_create. يبقى قيد DB منفصلًا لكل عمود؛ لا ترحيل أو إعادة كتابة لهوية قديمة، وتمنع طباعة أي تعارض سابق وفق ADR 0012.

## قواعد السعر
السعر الأساسي للمتغير هو fallback صريح، ولا يوجد تخفيض نسبي ضمني أو جمع خصومات. PriceRule محفوظة للمراجعة: متغير وقناة تجزئة/جملة وفرع اختياري وعميل اختياري وحد كمية وفترة شاملة وسعر وحدة صريح. سعر العميل يحتاج فرعًا مرتبطًا بالعميل؛ لا قاعدة باسم عميل عابرة تلقائيًا للفروع. المبالغ Decimal بمنزلتين دون float أو تقريب إدخال زائد. السعر الصفري صالح ولا يعني غياب السعر.

ترتيب المطابقة حتمي: عميل+فرع أولًا، ثم فرع، ثم عام. داخل النطاق تختار أكبر min_quantity لا يتجاوز الكمية. القناة والتاريخ شرطان، والتاريخان شاملان. لا اختيار للأرخص ولا اعتماد ترتيب إنشاء الصفوف أو priority رقمية قابلة لتجاوز النطاق. إن تساوى ترتيب قاعدتين مطابقتين يرفض resolver المعاينة بدل اختيار واحدة خفية.

إنشاء قاعدة يأخذ AccessLock داخل معاملة ويعيد فحص الصلاحية، ويرفض تداخل فترتين نشطتين للنطاق والقناة وحد الكمية أنفسها، حتى مع طلبين متزامنين. قيود unique جزئية منفصلة للنطاق العام والفرع والعميل تعالج NULL في وحدانية بداية الفترة؛ قيود DB تثبت السعر غير السالب وترتيب التواريخ وحد الكمية واشتراط فرع العميل. رفض بقية تداخل الفترات في الخدمة مع القفل؛ ليس PostgreSQL exclusion constraint. SQL خارج الخدمات قد ينشئ تداخلًا، لكن resolver يرفض التعادل. لا ادعاء أن unique وحده يمنع كل تداخل.

لا تعديل لسعر/نطاق/تواريخ قاعدة محفوظة: أوقفها وأضف بديلًا. runtime يسمح UPDATE(active) فقط، ولا DELETE. الإيقاف يؤثر فورًا على معاينات جديدة. لقطة quote_price تحمل الشركة والفرع والعميل والمتغير وإصداره وSKU والمواصفات والوحدة والقناة والتاريخ والقاعدة والمصدر وسعر الوحدة والإجمالي والعملة وtax_basis=exclusive. تغيير الكتالوج أو إيقاف القاعدة لا يغير قاموس لقطة سابقة. اللقطة ليست توقيعًا أو تفويض بيع؛ R10 يعيد التسعير والتفويض ويحفظ لقطة مستند الطلب/الفاتورة. R09/R10 يحسمان الضريبة والتقريب والترحيل؛ R11 يحسم أهلية استخدام قناة الجملة والآجل، ولا تمنح معاينة R07 حد ائتمان أو تخفيضًا معتمدًا للبيع.

## الوصول والواجهة
catalog.read مطلوب للقائمة والمتغير والسعر الأساسي المشترك داخل الشركة. catalog.manage مطلوب لكل تعديل وقاعدة سعر، وهو في القوالب الحالية لدى المالك. حساب الكاشير/المخزون يحتاج إسناد catalog_reader صريحًا لقراءة الدليل؛ لم نوسع دوره تلقائيًا. قوائم الأسعار الخاصة وبيانات عملائها لا تعرض للقارئ العام. إنشاء قاعدة فرع يتطلب وصول الفرع، واسم عميلها يتطلب customer.read وربطه بالفرع.

المعاينة تتطلب catalog.read وinvoice.read للفرع، وcustomer.read عند اختيار عميل. خيارات العملاء تُحمّل من فرع مخول فقط؛ معرف شركة/فرع آخر لا يمر من POST أو الخدمات. لا كشف أسماء عملاء من جميع الفروع في اختيار عام. نماذج POST مع CSRF وHTML وHTMX للبحث تعمل دون JavaScript؛ زر تحديث خيارات العملاء يعيد الخيارات دون حفظ ولو كان النموذج صالحًا. أُصلح busy-handler ليحفظ اسم وقيمة زر submit قبل تعطيله، لأن المتصفح يسقط الزر المعطل من FormData.

## مراجعة حقول الملاءمة المرجعية
- sigmant_right/left: ارتفاع تركيب مرتبط بالعدسة/الإطار والطلب؛ يوحد إلى قياس بالمليمتر لكل عين في R10، لا صفة عامة لـSKU.
- vertical_distance_right/left: يُراجع معنى المصطلح مع مسار الملاءمة R10 قبل تحويل النص القديم إلى vertex distance؛ لا نفترض وحدة أو معنى من الاسم فقط.
- a_v_right/left: حدّة بصر تخص الفحص وليست المنتج. النص مثل6/6 ليس Decimal واحدًا؛ يبقى المرجع والملاحظات في R06 حتى تحديد حقول قياسها مع تدفق الوصفة المستخدمة R10.

هذه مراجعة وتحديد موضع البيانات، وليست نقلًا لهذه الحقول. لا حذف لمعارف المرجع أو ادعاء ترحيلها تلقائيًا.

## الإثبات والحدود
المراجع التقنية التي راجعت: [Django constraints](https://docs.djangoproject.com/en/5.2/ref/models/constraints/) لقيود check/unique الجزئية و[aggregation](https://docs.djangoproject.com/en/5.1/topics/db/aggregation/) لتجنب تضاعف counts عند البحث عبر علاقات متعددة. يختبر PostgreSQL إنشاء المتغيرات والتكرار/التزامن والعزل والمنح والأسعار، واختبارات نقية تثبت مخططات الأنواع، وChromium يثبت النماذج والبحث والسعر الصفري وrefresh والهاتف وعدم JavaScript. لا اختبار مخزون أو محاسبة أو بيع أو ضريبة/ZATCA أو اعتماد طبي ضمن هذه المرحلة. النتائج الفعلية في TEST_LOG وSTATUS.
