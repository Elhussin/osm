# R02 — نموذج الوصول وملكية البيانات

التاريخ: 2026-11-09. مرجع التنفيذ: ADR 0003. هذه أسماء منطقية قبل النماذج؛ الترحيل الفعلي R03/R04.

تحديث التنفيذ R04: النماذج والخدمات موجودة الآن داخل access وidentity وdirectory. اعتمد ADR 0005 قوالب أدوار ثابتة بدل RolePermission قابل للتحرير؛ تعريفات الصلاحيات في policy.py والتعيينات فقط مخزنة في DB. شاشات الإدارة والتصميم وقناة تسليم الدعوات R05؛ التفاصيل في R04_CHECKLIST.md.

## النماذج والقيود
| النموذج | الموضع | القواعد |
|---|---|---|
| Company | public | UUID، schema_name ثابت فريد، state (initializing/ready/failed/suspended)، لا حذف تلقائي للمخطط |
| CompanyDomain | public | host كامل فريد بعد normalization، الشركة، domain معتمد فقط؛ لا host يقدمه العميل لتبديل schema |
| User | tenant | UUID، اسم دخول فريد داخل الشركة، hash كلمة مرور، is_active؛ لا company memberships ولا FK إلى HR؛ انتماؤه لمخططه ثابت |
| Branch | tenant | UUID ورمز فريد وحالة active ونوع متجر/مستودع؛ لا خلط بين مفتاح الفرع ورمز عرضه |
| Role | tenant | كود فريد واسم، permission codes من سجل صريح؛ role لا يمنح صلاحية بذاته دون assignment |
| RolePermission | tenant | unique(role, permission_code)، رفض أكواد غير مسجلة ومنح company-only داخل دور فرعي |
| RoleAssignment | tenant | user + role + scope(company أو branch)، branch مطلوب فقط للنطاق الفرعي؛ FK محلية وقيد فريد لكل تعيين |
| BranchAccess | tenant | وصول user لفرع active، فريد(user, branch)، يلغى دون حذف تاريخ المستندات؛ صلاحيات الفرع تحتاجه حتى مع تعيين دور فرعي |
| AuditEvent | tenant | actor UUID، فعل/مورد/فرع وrequest ID ووقت، metadata منقحة؛ لا حذف من واجهة الأعمال أو تخزين كلمات مرور وبيانات مرضى كاملة |
| ProviderConnection | tenant | فرع + provider + environment + provider_id + secret_ref، فريد وفق نوع الموصل؛ عرض إعداد الربط لا يعرض السر الخام |

CompanyContext ليس model يرسله المتصفح، بل قيمة تبنيها طبقة طلب/مهمة موثوقة. كل معرف resource يقرأ بعد حل المخطط. اختبارات السياسة تحمل company UUID صريحًا لكشف أخطاء تمرير سياق غير متطابق؛ هذا لا يعني إضافة company_id تلقائيًا إلى كل جدول tenant.

## المستندات وبيانات المرجع
- الفاتورة والطلب والوصفة والحركة والمطالبة لها فرع مالك لا يتغير بعد الترحيل، وFK إلى العميل/المنتج داخل الشركة. إنشاء المستند يستخلص الفرع المسموح على الخادم، ولا يثق بـcreated_by أو state أو provider_id من النموذج.
- العميل سجل شركة مع روابط CustomerBranchAccess واضحة؛ موظف فرع لا يرى ملفًا طبيًا لفرع آخر تلقائيًا. قراءة العميل/الوصفة تحتاج رابطًا لفرع مسموح، والتعديل أو مشاركة الملف يحتاج سياسة صريحة؛ تعدد الروابط لا يكشف تاريخ كل الفروع. تفاصيل التنفيذ R06، واختبار منع التسريب إلزامي.
- المنتجات وكود الخدمة وقوائم المرجع داخل الشركة. القراءة المشتركة تمنح صراحة على مستوى الشركة للأدوار المحتاجة، ولا تعني صلاحية إدارة السعر أو المخزون أو تكلفة الشراء.
- التقارير والقوائم تصفى على الفروع المسموحة لكل فعل؛ الحصول على قائمة IDs مرئية ليس إذن تعديلها. التصدير يستخدم نفس نطاق القراءة وصلاحية export منفصلة.
- نقل المخزون له مصدر ووجهة؛ نطاق التفويض يحتوي كليهما ويحتاج صلاحية النقل والوصول للفرعين.

## الأدوار الأولية
تفاصيل الصلاحيات القابلة للتنفيذ في rebuild/access/policy.py. هذه قوالب بذور R04، وليست جميع احتياجات ERP النهائية.

| الدور | نطاق التعيين | الغرض والحدود |
|---|---|---|
| owner | شركة فقط | جميع الأفعال المسجلة داخل شركته؛ لا صلاحيات شركة أخرى. نقل الملكية عملية منفصلة مع إعادة تحقق وهوية بديل نشط ومنع فقد آخر مالك |
| company_admin | شركة فقط | إدارة الشركة والأعضاء والأدوار والفروع؛ لا ترحيل مالي أو إعداد وصيل أو نقل ملكية تلقائيًا |
| accountant | شركة فقط | قراءة فواتير ودفعات وترحيل دفتر وتقارير؛ لا إدارة هويات أو أسرار التكامل |
| branch_manager | فرع فقط | عمليات البيع والدفع والمخزون لفرعه؛ لا إدارة أدوار أو إعداد التكامل |
| cashier | فرع فقط | إنشاء بيع واعتماده وتسجيل دفعة؛ لا عكس دفعات أو تصدير طبي أو إدارة مخزون |
| optometrist | فرع فقط | قراءة ملف مصرح وكتابة وصفة؛ لا تسجيل دفع أو تعديل أسعار |
| inventory_clerk | فرع فقط | قراءة وحجز ونقل مخزون؛ النقل يحتاج تعيينًا ووصولًا في الفرعين |
| insurance_officer | فرع فقط | بيانات العميل والوصفة اللازمة، تجهيز/إرسال طلب التأمين عند توفر الخدمة؛ لا إعداد أسرار وصيل أو دفتر الأستاذ |
| integration_admin | شركة فقط | إعداد ربط المزود، دون قراءة الوصفات أو إرسال المطالبات تلقائيًا |
| catalog_reader | شركة فقط | قراءة دليل المنتجات المشترك دون تعديل الأسعار أو معرفة الأرصدة والتكاليف |

الأفعال company-only (مثل members.manage وprovider.configure وcatalog.read) لا تُمنح من تعيين دور فرعي. لذلك قوالب الأدوار الفرعية لا تحتوي catalog.read؛ يمكن إسناد دور catalog_reader بنطاق الشركة صراحة لمستخدمي الفروع عند الحاجة. هذا فصل بين القراءة المشتركة وإدارة بيانات الفرع.

## سياسة التقييم
الافتراضي رفض. يشترط مستخدمًا موثقًا ونشطًا وشركة جاهزة، وتطابق الشركة في السياق والمستخدم والمورد. الأفعال المجهولة تُرفض حتى للمالك. تعيينات دور لشركة أو مستخدم آخر أو دور مجهول/ملغى لا أثر لها.

للفعل الفرعي يجب أن تكون فروع المورد غير فارغة ومعروفة ونشطة. يلزم BranchAccess لكل فرع مطلوب؛ المالك والأدوار الشركة لا تتجاوز شرط نشاط الفرع أو الوصول الصريح له. في R04 يمنح provisioning المالك وصولًا لكل فرع حالي، وخدمة إنشاء فرع تمنح وصوله للمالكين داخل المعاملة. لا يكفي تغيير selected_branch في الواجهة.

تحسب تغطية الصلاحية لكل الفروع المطلوبة من التعيينات النشطة؛ يلزم تغطيتها كلها. company assignment ذو صلاحية فرعية يغطي الفروع التي للمستخدم BranchAccess إليها، ولا يخلق وصولًا للفرع بنفسه.

هذه السياسة تحسم الوصول فقط؛ لا تفحص صحة مبالغ الفاتورة أو حالة الموافقة أو CSRF أو إعادة المصادقة. الخدمات تفحص قواعد العمل وتمنع التكرار وتدقق الأثر بعد السماح.

## إدارة الامتيازات والملكية
لا واجهة CRUD خام لـRoleAssignment. فحص members.manage/roles.manage لا يكفي وحده لمنح كل الأدوار: خدمة المنح ترفض منح أي فعل لا يملكه المنفذ في النطاق نفسه، وتمنع منح owner إلا بخدمة نقل ملكية، ومنح نطاق شركة من تعيين فرعي. تعديل Role يطبق نفس فحص الأثر على كل المستخدمين المتأثرين. لا يسمح company_admin بتحويل نفسه إلى owner أو accountant بمجرد تحرير role.

نقل الملكية وإلغاء آخر مالك يحتاج قفلًا ومعاملة وفحص بديل نشط وإعادة مصادقة وتدقيق. حذف مستخدم أو فرع مرتبط بمستند تاريخي يتحول إلى تعطيل، لا cascade لدفتر الأستاذ أو التأمين. حسابات الخدمة للتكامل محلية ومحددة العمليات وغير صالحة للدخول التفاعلي.

## أثر القرار على الكود القديم
لا تنقل User.client وBranchUsers المرتبط بـEmployee ولا تجاوز is_superuser ولا فصلًا يعتمد فقط على IsAuthenticated. تُحتفظ ملفات المرجع حتى R04، ثم تحذف بعد نجاح اختبارات بدائلها. لا تغيير أو حذف لقاعدة قديمة أو migrations في R02.

## امتداد R08-M01
أضيف stock.receive للمالك ومدير الفرع وموظف المخزون، وstock.reverse للمالك فقط، مع BranchAccess ونشاط الفرع وإعادة الفحص في الخدمة. لا تعديل حر لقوالب الأدوار أو منح تلقائي لـcatalog.read؛ يلزم catalog_reader للدليل/المصفوفة. إنشاء متغيرات ناقصة داخل المصفوفة يتطلب catalog.manage مستقلًا. الأدلة والحدود في ADR 0009؛ الحجز/الصرف والتحويل/الجرد لاحقًا في بقية R08.

## امتداد R08-M02
stock.issue للمالك ومدير الفرع وموظف المخزون فقط، مع stock.read وcatalog.read وBranchAccess. stock.reserve للحجز والتحرير والإلغاء، وstock.reverse لعكس الصرف للمالك فقط. لا تجاوز للمستخدم superuser أو لدور الكاشير أو لقارئ الكتالوج. التفويض يعاد حتى عند إعادة مفتاح طلب ناجح، وتظل هويات الحجوزات وأحداثها محمية على PostgreSQL وفق ADR 0010.

## امتداد R08-M03
stock.transfer وstock.read مطلوبان للمصدر والوجهة معًا، مع catalog.read، ولا يظهر مستند النقل إلا بقراءة الطرفين. stock.count للمالك ومدير الفرع فقط لاعتماد جرد الرصيد؛ موظف المخزون لا يعتمد التسوية. stock.reverse للمالك على جميع أطراف الأصل. اللقطة المستخدمة لأعلام الأزرار لا تمنح اعتمادًا؛ الخدمات تعيد التفويض داخل القفل حتى replay. التفاصيل ADR 0011.

## امتداد R08-M04
الأذونات الحالية تنطبق على الأصناف المتتبعة دون أدوار جديدة. اختيار position لا يمنح وصولًا؛ يعاد التحقق من الشركة والفرع والصنف والفعل داخل الخدمة. سجل الحركات يرشح بفرع الحركة التاريخي، حتى بعد انتقال موضع الجهاز إلى فرع آخر. لا تمنح صلاحية قراءة الجهاز الحالية قراءة جميع فروع تاريخه. التفاصيل ADR 0013.

## امتداد R09-M01
قراءة وحفظ الملف الضريبي تحتاج company.manage الحية؛ لا امتياز جديد لقالب accountant أو integration_admin أو superuser. الملف بيانات قانونية على مستوى الشركة لا أرصدة فرع؛ لا يقبل company/schema من المتصفح. النسخ ثابتة وإذنها يعاد قبل replay. إعداد شهادات وبيئات مزود حقيقي يبقى provider.configure في R13 ولا تمنحه شاشة الملف. لا صلاحية إرسال أو إصدار تنشأ من اكتمال البيانات.

## امتداد R09-M02
دليل الحسابات والفترات إعدادات شركة تقرأ بـledger.read وتكتب بـledger.read وledger.post معًا؛ القوالب القائمة للمالك والمحاسب كما هي. company.manage لا يمنح ذلك لمسؤول الشركة؛ لا منح تلقائي لدور فرعي أو superuser. لا قيود أو أرصدة فرع من هذه الصلاحية العامة في M02. الخدمات تعيد التفويض قبل replay، والأب ومعرف الفترة يحلان داخل المخطط الحالي فقط.

## امتداد R09-M03
مسودات القيود والقيود المرحّلة موارد فرعية: ledger.read/read+post مع BranchAccess صريح ونشاط الفرع. تختار القائمة فروع ledger.read قبل البحث والحد والعد وlookup، وتعيد الخدمات التفويض داخل AccessLock حتى replay. دور المحاسب وحده لا ينشئ وصول فروع؛ يمنح عبر access.services. إعدادات الحسابات والفترات شركة عامة كما في M02، ولا تكشف تفاصيل قيود فروع أخرى. إلغاء الفترة يفحص الارتباط على مستوى الشركة دون كشف بيانات الأسطر.

## امتداد R09-M04
تقارير القراءة تحتاج ledger.read حيًا وتجمع فقط visible_branches الصريحة النشطة. تحديد فرع غير مصرح يرفض ولا يعود لكل الفروع؛ بلا فروع أرقام صفرية. إعداد الحساب المشترك لا يمنح أرقامه. المجاميع تسبق البحث والصفحات داخل النطاق المصرح، وروابط المصدر تخضع لتفويض M03. لا أدوار جديدة أو تجاوز superuser.

## امتداد R10-M01
إدارة تعريف صندوق البيع تحتاج company.manage وledger.read وledger.post مع payment.read ووصول الفرع الصريح والنشط. القوالب ثابتة؛ يسمح جمع company_admin وaccountant مع وصول الفرع، ولا يكفي أي منهما منفردًا أو superuser. registers_for يرشح قبل البحث والعد والصفحات؛ الكاشير لا يغير إعداد الحساب، واستخدامه للوردية يبنى في M02. لا هوية شركة أو فاعل من POST.
